before we start, the honest state of the art

Three times is not a test suite.

Here is how most AI features get built today. You write a prompt, try three examples on your laptop, nod at the screen, and push it live.

Ten minutes later a real customer asks something slightly unfamiliar and the whole thing falls apart. You are shipping on vibes.

Descript, Bolt and Anthropic's own Claude Code all started this way — hit the wall where vibes stop working, and built evals.

stop one — why we cannot just use normal software tests

Two answers can share zero words and both be right.

In normal software, two plus two is four. If the function returns five, the test turns red.

Ask an AI the same question twice and you get two completely different sentences. Both are helpful. Both are true. A normal test checks for exact words, so it fails a good answer just for phrasing it differently.

You cannot test for an exact string. You have to test whether the answer did the job.

normal software test

2 + 2 → must equal "4"

one right string, every single run

AI run 1

"Apple grew revenue 6% this quarter, led by services."

AI run 2 — same prompt, 2 seconds later

"Quarterly sales at Apple rose six percent on strong services growth."

Exact string match: FAIL — even though both are right

Four things you cannot do without evals.

1 · stop playing whac-a-mole

Fix one thing without breaking another

you make the tone warmer, and quietly break how it quotes prices

2 · settle the argument

Tell whether prompt B beats prompt A

instead of two people in Slack waving three screenshots each

3 · swap models in an afternoon

Try a new model before lunch

new models drop every few months; without evals, switching takes weeks of nervous clicking

Block a bad change before customers see it

write this one down ★

Traces tell you what happened. Evals tell you if it was good.

1 · Traces = logs, for AI

The complete diary of one run

Records every step as a tree of spans: what the customer asked, which tools the agent called, what the search returned, how many tokens it spent, and what it answered.

2 · Evals = tests, for AI

The grader that marks the diary

Reads that trace afterwards and scores it against your rules. Did it answer the question? Did it stick to the facts? Would a real customer trust this reply?

Laurie Voss's rule: you cannot grade what you did not record. Tracing always comes first.

single prompts are one step. agents are a chain.

One wrong turn early poisons the whole run.

A plain model call is one step: question in, answer out. An agent takes a dozen steps on its own — searching, reading, deciding whether to search again, and writing.

If step one goes slightly sideways, every step after it builds confidently on the mistake.

Each step worked. The whole answer is still wrong.

customer asks

"Tell me about Tesla." (meaning the car company)

step 1 · web search

Pulls biographies of Nikola Tesla, the 1890s inventor

step 2 · report writer

Writes a clear, well-structured essay on alternating current

what the customer sees

Polished, grammatical, and completely useless

the trap teams fall into when testing agents

Grade what it finished, not the route it took.

Because an agent chooses its own steps, it is tempting to test that it called the exact tools you expected in the exact order.

Do not do that. An agent might search four times on Tuesday and six times on Wednesday and still write a great answer. If you police the path, you punish the agent for being clever.

from Anthropic's customer-service benchmark (τ²-bench)

A traveller asked to move an economy flight. Airline policy said economy tickets cannot be changed — so the test expected the agent to refuse. Instead, the agent spotted that policy did allow upgrading economy to first class, and first-class tickets can be moved. It upgraded the ticket, moved the flight, delighted the traveller — and failed the benchmark.

Score the outcome. Only police the steps when order is a safety rule — like checking ID before a refund.

stop two — the three ways to grade an AI

Stack them like Swiss cheese.

layer 1 · milliseconds, free

Code checks

Plain code. Is it valid JSON? Under 500 words? Did it include the stock ticker? Did it say "As an AI language model"?

hole: blind to meaning

layer 2 · seconds, pennies

AI as a judge

A second model with a clear marking sheet. Grades whether the answer stuck to the source notes, answered the question, and gave actionable advice.

hole: misses brand-new weirdness

layer 3 · minutes, expensive

Human review

Domain experts reading real traces. Spots novel failure modes you never thought to test for, and keeps the AI judge honest.

hole: humans get tired and miss 50% of bugs

Every slice has holes. Stack all three so the holes never line up.

watch the cheese stack up

two jobs for the exact same eval

First a hill to climb. Then a guardrail.

stage 1 · when you are building

Capability eval ("Can it do this at all?")

Starts at a low score — say 45%. That gap is your hill to climb. Every time you improve the prompt or the tools, the score tells you whether you actually climbed higher.

stage 2 · once it works

Regression eval ("Did we slide back?")

Once you reach nearly 100%, you do not throw the test away. It runs automatically on every change so a future edit never quietly breaks what you already fixed.

Today's capability hill is next month's regression guardrail.

the turning point at 18:55 in the talk ★

A score says it failed. An explanation says how to fix it.

Every eval returns a score (1 or 0) and a label (correct or incorrect). An AI judge adds a third piece: one plain sentence explaining why.

example · budget travel planner (t = 18:55)

Label: incorrect (0)
Explanation: "The agent gave destination info and hotel ideas, but the user asked for budget travel and there were no cost estimates."

That one sentence turns an eval from a scoreboard into a debugging tool.

1 · stop reading every trace by hand

the explanation tells you what broke in one glance

2 · spot the pattern across 50 failures

when 30 failures all say "no cost estimates," you have found a systematic root cause

3 · feed the explanations to your coding agent

hand the failing traces and judge explanations to Claude Code or Copilot — and let it fix the prompt

stop three — watching a real agent fail in the wild

Two steps, two lines of tracing.

input

Stock question

"Is Microsoft cloud growth a buy right now?"

turn 1 · researcher

Search the web

runs 4 to 10 live web searches for revenue, margins and risks

turn 2 · writer

Write the report

turns the research notes into an investor briefing

open-source tracing

One parent trace

2 lines of OpenTelemetry wrap both turns into one diary

Laurie built this agent on a fast, cheap worker model (Claude Haiku) and ran 13 realistic questions through it — Apple vs. Microsoft, Amazon AWS, Coca-Cola dividends, Rivian, and casual prompts like "Yo, is Tesla a buy?"

Before writing a single eval, he did the most important step in the whole talk: he opened the 13 traces and read them.

rule number one — look at your data before writing a test

Ten reports looked great. Three vanished into thin air.

Ten of the 13 questions came back as rich, 5,000-character financial reports with tables and recommendations.

Three — including Microsoft and Rivian — came back as a single cheerful sentence: "The report is saved as Microsoft_Cloud_Segment_Financial_Report.md."

The agent had tried to use a file-saving tool inside a cloud notebook with no hard drive. The save failed silently, and the agent handed the user a pointer to a file that did not exist.

10 of 13 traces (3,000–7,000 chars)

Full financial report delivered inline in the reply.

3 of 13 traces (under 300 chars)

"Saved to Microsoft_Cloud_Report.md" — on a machine with no disk. Plus a loop of repeated searches.

Fifteen minutes reading raw traces teaches you more than an hour building dashboards.

how to read traces without drowning in them

First write plain notes. Then group the causes.

pass 1 · open coding

Just write down what went wrong

Read each trace and scribble plain, everyday notes. Do not invent categories yet.

"saved report to a disk that does not exist"
"wrote about AWS, forgot Amazon's stock ticker"
"made up a Q3 margin number not in the search"
"ended with vague 'consider various factors' fluff"
pass 2 · axial coding

Sort the notes into root-cause buckets

Group those notes by what kind of fix they need:

Tool / delivery failure — tried to write to disk
Scope violation — missed the parent ticker
Hallucination — invented numbers not in research
Reasoning gap — summary with no buy/sell call

Rank buckets by how often it happens × how bad it is. And let domain experts — not engineers — define "bad."

layer one of the cheese — five lines of Python

Did the Amazon report mention Amazon's ticker?

The first automated eval in the workshop is five lines of code: check all uppercase words in the report and verify the company's stock ticker (AAPL, MSFT, AMZN) is actually there.

Twelve reports passed. One failed: the question about Amazon's cloud division (AWS).

The agent got so absorbed in cloud numbers that it wrote a whole report about AWS and never once mentioned AMZN — the stock an investor actually has to buy.

layer two — bringing in an off-the-shelf AI judge

First judge: 0 out of 13. Second judge: 6 out of 13.

attempt 1 · built-in "Correctness" judge

0 pass · 13 fail

Why did every single report fail? Because the agent searched the live 2026 web, while the judge checked facts against its own frozen training memory — and complained that 2026 earnings numbers "came from the future."

attempt 2 · "Faithfulness" judge + Turn 1 search notes

6 faithful · 7 unfaithful

Instead of asking "Is this true from memory?", pull Turn 1's web search span out of the trace and hand it to the judge: "Did the writer stick to the notes it actually found?" Seven reports were caught inventing numbers.

Lesson: give the judge the exact same source material the writer saw — and now 6/13 is a real capability hill to climb.

layer three — why off-the-shelf judges are only a starting point

Generic judges do not know what "good" means here.

A stock report can mention the ticker and stick faithfully to the search notes, and still be a terrible financial report.

Most bad reports just summarise last year's numbers and end with polite mush: "Investors should consider various market factors."

In our domain, good means actionable: a clear buy, sell or hold call, numbers on the risks, and a view on what happens next.

passes generic evals, useless to an investor

"NVIDIA revenue grew 122% year-over-year. The company faces competition and macro risks. Investors should weigh these factors carefully."

passes our custom Actionability rubric

"Hold above $800; accumulate on pullbacks below $760. Trades at 35× forward P/E vs. 22× sector median, with ~70% revenue tied to four cloud buyers."

all five parts of a custom judge prompt, stacked up

How to write a marking sheet that works.

1 · Context & role

tell it what it is grading ("a financial report for actionable guidance"), not "you are a genius"

2 · Observable criteria

concrete yes/no checks lifted straight from your trace notes: buy/sell/hold, quantified risks, forward outlook

3 · XML tags around data

wrap <user_query> and <financial_report> so the judge never mixes up instructions and data

4 · Good & bad examples

one concrete pass and one concrete fail teach the boundary better than a page of adjectives

5 · Binary + reason first

score 0 or 1 (never 1-to-5), and make the judge write its explanation before choosing the score

Why never a 1-to-5 scale? Because neither humans nor models know the difference between a 3 and a 4.

three traps that quietly wreck eval suites

Three things not to do.

trap 1

The "God Evaluator"

One giant prompt grading factual accuracy, tone, formatting and actionability all at once. When it fails, you have no idea which one broke. Keep one judge per job.

trap 2

Treating rubrics like throwaway text

Changing three words in a judge prompt can swing your pass rate by 20%. Keep your eval prompts in version control and test them like production code.

trap 3

Mixing up Guardrails and North Stars

A hallucinated stock price is a guardrail (blocks the release, wakes someone at 2 a.m.). Suggesting a related stock is a north star (belongs on a weekly chart).

stop four — how do you know your AI judge is right?

Grade the judge against human decisions.

An AI judge is still an AI. You cannot trust it just because the prompt looks clever.

So you build a small golden dataset of real outputs that a human expert has already marked Pass or Fail. Use 75% to tune the judge's rubric, and hold out 25% as a blind exam.

In safety and quality checks, prioritise recall — a false alarm is cheaper than a bad report reaching a customer.

Anthropic's rule for meta-evaluation

Failures should seem fair. If an agent's answer fails your eval, and you read it and think "that looks fine to me," the bug is in your eval — not your agent.

When the judge and the human disagree, read the judge's explanation. Usually your rubric was vague, and tightening one line fixes it.

four ways an AI judge gets fooled

Four biases to watch for.

1 · length bias

Longer looks smarter

judges reward wordy, padded answers over short, right ones unless you tell them to ignore length

2 · confidence bias

Certainty beats truth

just like humans, models get fooled by an authoritative tone even when the numbers are invented

3 · position bias

First place wins

ask a judge to pick between Answer A and Answer B, and it will systematically favour whichever comes first

4 · self-preference bias

Models love their own voice

a model rates its own writing higher — use a stronger model (e.g. Sonnet grading Haiku) or a different provider

And always test both directions: check that the agent searches when it should, and stays quiet when it should not.

Let your coding agent fix the prompt.

1 · filter

Save the failures

2 · diagnose

Read the reasons

hand the judge's explanations + product rules to Claude

3 · rewrite

Edit the prompt

4 · experiment

Re-run the test

same inputs, same judges: score jumps from 46% to 100%

One warning from the workshop: never hand a coding agent the raw failing test cases by themselves. If you do, it will cheat and hard-code special rules for those ten stocks.

Give it the failure themes and the product requirements so it fixes the general behaviour.

practical numbers for Monday morning

How many examples, and what to fix first.

how big does my test set need to be?

12 to 20 examples to start

Enough to catch obvious bugs and get directional signal in an afternoon.

for real shipping decisions

200 to 400 examples in production

Human-scale, not millions. Halving your margin of error takes 4× as many examples, so 300 is the sweet spot.

where to spend your engineering hours (highest ROI first)
1 · highest leverage

Fix data quality & search retrieval first

the cleverest prompt in the world cannot fix stale or wrong search results

2 · best return per dollar

Tighten prompts, examples & explicit constraints

3 · costs latency and money on every call

Upgrade to a bigger model

4 · lowest leverage of all

Fiddle with temperature and top_p knobs

when offline tests meet real customer traffic

Run the same evals live in production.

Offline evals check your agent before you ship. Online evals run the exact same graders on live customer traffic (sampling 1% to 10% of conversations so AI judges stay cheap).

When a real customer finds a brand-new way to break your agent on Thursday night, the online eval flags it, saves that trace into your golden dataset, and your coding agent proposes a fix on Friday morning.

And before you build the next feature, write the eval first — Eval-Driven Development.

the compounding flywheel
1 · Live traffic → traces recorded automatically
2 · Online evals → flag bad runs & alert the team
3 · Golden dataset grows → real edge cases saved
4 · Coding agent + experiment → verified fix ships
